## Commercial / production-readiness

6. **DONE, fully verified (2026-08-07 and 2026-08-08); cross-process defect found and fixed 2026-08-08, see Bug 14.** Replaced the flat-JSON-only `TokenStore` with an abstract `StorageProvider` interface (`src/anonymize.py`): `FileStorageProvider` (the original behavior, still the default everywhere — `service.py`, `pipeline.py`, `validate.py` all pass a bare path and get wrapped automatically for backward compatibility) and `RedisStorageProvider`, new, for a shared production backend across multiple `redact-service` replicas. `RedisStorageProvider` first passed against a live Redis instance (`validation/redis_storage_provider_test.py`, run by the user locally against `redis:7`): basic token round trip, persistence across a fresh `TokenStore`/provider instance pointed at the same Redis, tokenize/detokenize round trip, and the same 8-threads-x-200-calls concurrent-access test that originally found the TokenStore race condition (Bug 6) — zero errors across all of it. That test only ever exercised multiple *threads* in one process, though, not the real production topology of multiple separate `redact-service`/gunicorn-worker *processes* sharing one backend — a gap this item's original text flagged explicitly. **Update 2026-08-08 (Bug 14):** building the actual multi-process test closed that gap, and the gap turned out to be hiding a real bug — `TokenStore.save()` did a blind read-once/overwrite-on-every-save, losing reverse-map entries whenever two processes saved concurrently. In-sandbox confirmation (no Docker needed), `validation/multiprocess_tokenstore_test.py` against `FileStorageProvider`: 58.7% loss pre-fix (plus worker crashes from a non-atomic file write), 14.2% loss after a read-merge-write fix alone, 0% loss once real cross-process locking was added (`FileStorageProvider.lock_for_save()` via `fcntl.flock`; `RedisStorageProvider.lock_for_save()` via a single-node Redis `SET NX PX` + Lua-release lock, deliberately scoped to single-node correctness rather than full Redlock). The Redis-backend counterpart of this test (`validation/multiprocess_redis_test.py`) was run by the user locally against a live Redis instance the same day: 8 processes x 50 tokens each, save-after-every-token, **0 of 400 tokens lost** — the cross-process lock held up under real separate OS processes, not just a logical analogy to the file backend. `RedisStorageProvider` is now verified for both single-process thread safety and multi-process safety, matching `FileStorageProvider`. A HashiCorp Vault provider isn't implemented; the interface is designed so adding one only means implementing `load()`/`save()`.

   **Extended 2026-08-08** (`validation/syslog_coverage_extension_test.py`, a dedicated small Faker-seeded corpus kept separate from `data/synthetic_logs.jsonl` so this didn't perturb any of the many numbers already tied to that file's exact content): four more common real-world syslog message shapes now covered — sshd `Accepted publickey for X from Y port Z` (key-based auth; the original patterns only had `Accepted password for`, an oversight, not a scope decision), `su` privilege-escalation (`session opened for user root by X(uid=N)`), `useradd`/`usermod` (`name=X, UID=N, GID=N, ...`, comma-separated rather than sudo's semicolon-separated KV), and `dhclient` DHCP lease messages (`DHCPACK from X`, `DHCPOFFER from X`). All five new shapes measured at 100% coverage (500/500 across 100 Faker-generated lines per shape), zero regression on the original shapes (300/300, unchanged), zero false extraction on clean lines including a deliberately-included still-uncovered `cron` line (0/300).

   **A real ordering bug was found and fixed building this test**, not just missing coverage: the `su` and `dhclient` message shapes both legitimately contain a bare `=` in a non-KV context (`by jsmith(uid=0)`, `(xid=0x12345678)`), which used to trigger the function's generic KV-fallback branch first (it only checked `if "=" in rest`) and produce a wrong, nonsensical field (e.g. `su.uid = "0)"`) instead of ever reaching the more specific patterns. Fixed by trying the preposition-shaped patterns before the generic KV fallback, not after — full writeup in the script's own docstring and `extract_fields_syslog`'s.

**2026-08-08: run at 1,000,000 lines — FAILED, and found the most consequential bug of this entire roadmap (Bug 15, `BUGS_AND_FIXES.md`).** The run's own reconciliation reported FAIL (728,125 of 1,000,000 expected events at harness exit), and live investigation confirmed this wasn't the harness quitting early on a slow patch (the leading theory at first) — ingestion was still genuinely, severely stalled minutes later (916,500 and barely climbing), with `redact-service` pegged at ~110% CPU producing ~3 events/sec while `redact-logstash` sat nearly idle waiting on it, and zero errors anywhere in any container's logs. Root-caused directly: `docker exec redact-service ls -la /app/output/` showed `token_store.json` at 12.4MB/93,279 entries, and a single live request timed with `curl` took 2.927s. `TokenStore.save()` (the fix Bug 14 introduced) does a full read-merge-write of the ENTIRE persisted store on every call, and `service.py` calls it after every single request — O(n) cost per request, O(n²) total across a run, invisible at every scale tested before this one (10,000 and 100,000 lines both stayed too small to cross the point where this became noticeable). **A debounce mitigation was applied and verified in-sandbox the same day** (`save_every_n_calls` parameter, `service.py` now defaults to a real write once every 25 requests instead of every one; confirmed via a new dedicated test, `validation/tokenstore_save_scaling_test.py`, showing ~47x less total time spent in `save()` with zero regression on the existing multi-process zero-loss tests) — but this is a mitigation, not a fix (same O(n) shape, just paid less often), and introduces a new bounded crash-recovery-window tradeoff. **Re-run against the mitigation, same day — PASS.** After tearing down the stuck stack (`docker compose down -v`) and rebuilding, a fresh `run_load_test.sh 1000000` run reported its own `FAIL` at exit (938,000/1,000,000 after the harness's poll loop hit its fixed 240-iteration cap) — but manually re-running `reconcile.py` minutes later showed the count still climbing steadily (971,625 → 981,750 over 180s, ~56 events/sec, clearly not stalled), and a further 600s wait produced a clean, complete result: **`security-logs-anonymized-*` = 1,000,000 exact, `security-logs-quarantine-*` = 0 exact, `redact-audit-trail-*` = 893,150, reconciliation PASS.** 89.315% audit fan-out closely matches the 100,000-line run's 89.159%, confirming correctness held at 10x scale, not just completion. 12. **SCOPED AND DOCUMENTED, 2026-08-09; IMPLEMENTED 2026-08-10; CONFIRMED WORKING LIVE, 2026-08-11 — see the updates below.** Two related production-scale questions this project has always flagged as genuinely open (README.md's "Known limitations" section, and item 9/the 1,000,000-line load test's own closing caveat): whether Logstash's synchronous `http` filter is the right shape for real production volume, and whether multiple `redact-service` replicas sharing one `TokenStore` backend actually behave correctly under real concurrent load rather than just in principle. Both need real infrastructure this development environment doesn't have (a message broker, multiple real machines or a container orchestrator actually scheduling replicas across them, a load balancer) — this item is a design writeup and an explicit list of what a real test would need, not a claim that either has been built or verified.

    **Queue decoupling (Redis Streams or Kafka in front of `redact-service`, replacing Logstash's synchronous `http` filter call):** today, `redact-pipeline.conf`'s `http` filter (`pipeline.workers => 8`) blocks each of its 8 worker threads on a full round trip to `redact-service` per event — confirmed directly by this project's own load testing (item 9 above): throughput held at ~250 lines/sec at 100,000-line scale and ~224 lines/sec at 1,000,000-line scale, essentially flat, which is consistent with `redact-service`'s own per-request cost (CPU-bound NER, GIL-serialized within each gunicorn worker) being the actual bottleneck Logstash is waiting on, not Logstash itself. A queue in between (Logstash publishes raw events to a Redis Stream or Kafka topic; one or more consumer processes pull from it, call `redact-service`, and write results onward to OpenSearch) would decouple ingestion rate from anonymization throughput — Logstash could keep reading input at whatever rate the source produces it, rather than blocking on `redact-service`'s own pace, and a burst of input would queue rather than back up through Logstash's own pipeline. This is a real architectural improvement for burst tolerance and backpressure, not a magic throughput fix: the NER call's CPU-bound, GIL-serialized cost per event doesn't go away by adding a queue in front of it — it still needs either more `redact-service` replicas (see below) or a faster detection path (e.g. the field-level NER gate, item 5/task 5 of the 2026-08-09 engineering pass) to actually process faster. Concretely unverifiable here: which of Redis Streams (simpler, this project already depends on Redis for `RedisStorageProvider`, consumer groups give at-least-once delivery with acknowledgment) vs. Kafka (more operational overhead, but standard for this at real enterprise log volume, better long-term retention/replay story) is the right choice depends on operational constraints (existing infrastructure, retention requirements, ops team familiarity) this project has no specific deployment target to evaluate against — stated here as the open decision it is, not resolved with a guess.

    **Multiple `redact-service` replicas behind shared Redis-backed `TokenStore`, tested via `docker compose up --scale redact-service=N`:** this is much closer to already being true than the queue question — `RedisStorageProvider` is verified for real cross-process concurrency (`validation/multiprocess_redis_test.py`, 8 separate OS processes x 50 tokens each, 0/400 lost, see Bug 14/item 6), and gunicorn's own `--workers $(nproc)` setup already means every single-container deployment of `redact-service` is multiple OS processes sharing one backend, which is most of what a multi-*replica* deployment would add. What's NOT verified is the piece specific to actual replication: multiple separate `redact-service` **containers** behind a shared entry point, with Logstash's `http` filter load-balancing or round-robining requests across them (Docker Compose's built-in DNS round-robin for a scaled service, or a real reverse proxy/load balancer in front). `docker compose up --scale redact-service=N` is the concrete, low-effort way to test this — it doesn't need Kubernetes or cloud infrastructure, just a Compose file where `redact-service` isn't pinned to a single container name/port the way `docker-compose.yml` currently has it (a small, mechanical config change: drop the fixed `container_name`/host port mapping, let Compose assign the pool). A real test would confirm what this project's own multiprocess test already suggests should hold — no lost tokens, no duplicate-token drift across replicas, correct `resolve()` regardless of which replica's Redis view a request lands on — but "should hold based on the multiprocess test" is an inference, not the same as having actually run it against real separate containers with real Docker networking, container restarts, and Compose's actual load-balancing behavior in the loop.

    **IMPLEMENTED, 2026-08-10 — moved from "scoped, not implemented" to "built, verification pending the user's machine."** Both pieces above now have real code, not just a design writeup. Multi-replica: `docker-compose.yml`'s `redact-service` no longer declares a fixed `container_name` or host port (both block `--scale`), a new `redact-lb` nginx service proxies to the pool using `resolver 127.0.0.11 valid=5s` plus a variable in `proxy_pass` (the documented technique for actually re-resolving Docker's embedded DNS per request rather than caching one replica's IP for the life of a connection — see `logstash/nginx-lb.conf`'s own comment for why relying on Compose's DNS round-robin directly, without a real proxy, was rejected as unverifiable), and `redact-pipeline.conf` now points at `redact-lb` instead of `redact-service` directly. `Dockerfile`'s gunicorn `CMD` gained `--access-logfile -` specifically so per-replica request counts are checkable from `docker compose logs` afterward, rather than assuming distribution worked just because reconciliation passed (a single working replica is enough for reconciliation alone to look correct). Queue decoupling: verified via live Logstash plugin documentation (2026-08-10, not assumed) that the *official* `logstash-output-redis` plugin supports only `data_type => list` (RPUSH) / `channel` (PUBLISH), **not** Streams/XADD — a separate, unofficial `logstash-output-redis-streams` plugin (redis-field-engineering, not the `logstash-plugins` org, low visible adoption) claims XADD support but is unverified in this project, and given this exact session's own Bug 16 (a one-character Logstash config mistake that silently crashed the whole pipeline for hours before being caught), building the "closed for good" queue path on an unverified plugin was rejected as too risky to call done.
