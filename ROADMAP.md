## Commercial / production-readiness

6. **DONE, fully verified (2026-08-07).** Replaced the flat-JSON-only `TokenStore` with an abstract `StorageProvider` interface (`src/anonymize.py`): `FileStorageProvider` (the original behavior, still the default everywhere — `service.py`, `pipeline.py`, `validate.py` all pass a bare path and get wrapped automatically for backward compatibility) and `RedisStorageProvider` (new, for a shared production backend across multiple `redact-service` replicas). **`RedisStorageProvider` verified against a live Redis instance** (`validation/redis_storage_provider_test.py`, run by the user locally against `redis:7`): basic token round trip, persistence across a fresh `TokenStore`/provider instance pointed at the same Redis, tokenize/detokenize round trip, and the same 8-threads-x-200-calls concurrent-access test that originally found the TokenStore race condition (Bug 6) — all passed, zero errors. The in-process `threading.Lock()` guarantee does carry over correctly here because this test still ran within one process; multi-*process* concurrent writes across separate `redact-service` replicas sharing one Redis backend (the actual production topology this provider is for) has not been tested and would need Redis-side atomicity (e.g. `SETNX`/Lua scripting) rather than relying on the Python-level lock, which only protects one process's threads. A HashiCorp Vault provider is not implemented; the interface is designed so adding one only requires implementing `load()`/`save()`.
7. **DONE, fully verified (2026-08-07).** `Dockerfile` now runs `redact-service` under gunicorn (`--workers $(nproc)`, matched to CPU cores) instead of Flask's dev server. `src/service.py`'s model-warmup call was moved to module level specifically so it fires under gunicorn's import-based worker model too, not just `python src/service.py`'s `__main__` guard. **Full Docker Compose stack rerun, run by the user locally:** fresh `docker compose down -v && python src/export_raw_logs.py && docker compose up --build` — `redact-service`'s log shows 8 `Booting worker` lines (host core count) and reports healthy quickly; final `_search?size=0` reconciliation: `security-logs-anonymized-*` = 10,000, `security-logs-quarantine-*` = 0, exact match against the 10,000 exported lines. gunicorn confirmed working end-to-end, not just smoke-tested standalone. FastAPI/Uvicorn remains a further-out rewrite, not a drop-in swap, and only worth it if async I/O actually becomes the bottleneck (the NER call is CPU-bound and GIL-serialized regardless of web framework).
8. **DONE (partial), 2026-08-07; extended, 2026-08-08.** Added `extract_fields_syslog()` to `fields.py`: recognizes KV-style syslog bodies (`sudo`, `kernel` templates) and sshd auth-message shapes (`Failed password for X from Y port Z`, `Invalid user X from Y`, etc.). Measured against the regenerated synthetic corpus: 100% of PII-bearing syslog entries (1,035/1,035) now produce field-level structure (0% before), zero false extractions on 2,347 clean syslog entries, and `drift.py`'s own hit-rate logic correctly separates the PII-bearing fields (`sshd.user` ~48%, `sudo.PWD` ~51%) from the constant ones (`sudo.USER` 0%). No spaCy needed for this verification since it's regex-only, so it was fully testable in this sandbox, unlike items 3-5 above.

   **Extended 2026-08-08** (`validation/syslog_coverage_extension_test.py`, a dedicated small Faker-seeded corpus kept separate from `data/synthetic_logs.jsonl` so this didn't perturb any of the many numbers already tied to that file's exact content): four more common real-world syslog message shapes now covered — sshd `Accepted publickey for X from Y port Z` (key-based auth; the original patterns only had `Accepted password for`, an oversight, not a scope decision), `su` privilege-escalation (`session opened for user root by X(uid=N)`), `useradd`/`usermod` (`name=X, UID=N, GID=N, ...`, comma-separated rather than sudo's semicolon-separated KV), and `dhclient` DHCP lease messages (`DHCPACK from X`, `DHCPOFFER from X`). All five new shapes measured at 100% coverage (500/500 across 100 Faker-generated lines per shape), zero regression on the original shapes (300/300, unchanged), zero false extraction on clean lines including a deliberately-included still-uncovered `cron` line (0/300).

   **A real ordering bug was found and fixed building this test**, not just missing coverage: the `su` and `dhclient` message shapes both legitimately contain a bare `=` in a non-KV context (`by jsmith(uid=0)`, `(xid=0x12345678)`), which used to trigger the function's generic KV-fallback branch first (it only checked `if "=" in rest`) and produce a wrong, nonsensical field (e.g. `su.uid = "0)"`) instead of ever reaching the more specific patterns. Fixed by trying the preposition-shaped patterns before the generic KV fallback, not after — full writeup in the script's own docstring and `extract_fields_syslog`'s.

   **Still explicitly partial**: message shapes outside this now-9-pattern list (other daemons, other wording — NetworkManager, systemd unit failures, cron with PII-bearing arguments, and any auth wording not in the sshd list) still get zero fields, same as before — a production deployment with different syslog traffic needs its own additional patterns, following the same approach.

**Unplanned but significant side finding, fixed the same session:** measuring whether `drift.py` actually caught injected drift in a newly-covered syslog field surfaced Bug 11 (`BUGS_AND_FIXES.md`) — `field_stats()` never called `scan_flattened()`, so drift detection was structurally blind to flattened-username PII in every field it monitors, in every log type, since Layer 4 was added. Fixed (now included by default, `use_ner` made an optional parameter for testing without spaCy). Confirmed via injection test: previously silent, now correctly flagged. One honest side-effect also found: the flattened layer's ~50% recall produces enough sample-to-sample variance to occasionally cross the default 5% drift threshold on a stable corpus — noted, not treated as a defect, see Bug 11 for the full writeup. **`validate.py`'s own (NER-dependent) Section 5 drift check was rerun by the user locally against the fix**, confirming the same side-effect independently: 16/18 checks pass overall, with the 2 failures both in Section 5 and both matching the documented pattern (`syslog.sshd.user` riding along as a false positive alongside correctly-caught real drift) — see Bug 11 in `BUGS_AND_FIXES.md` for the full numbers.
9. **DONE, 2026-08-07, run by the user locally (three runs; first two cut short by a harness bug, third clean).** Load testing beyond demo scale: everything verified before this item was single-node, single-shard, one Docker Desktop machine, 10,000 lines. `validation/load_test/` (`run_load_test.sh N` + `reconcile.py`) ran a full, clean 100,000-line pass — 10x prior scale. **Final, verified result:** `security-logs-anonymized-*` = 100,000 exact, `security-logs-quarantine-*` = 0 exact, `redact-audit-trail-*` = 89,159 exact (matching the pipeline's own fan-out count precisely), no timeout/error bursts beyond the already-fixed Bug 3 startup cluster. True end-to-end throughput at this scale: **~250 lines/sec** (400s wall clock for 100,000 lines) — an earlier ~950-1,000/sec estimate from the first two (cut-short) runs was itself invalid, a byproduct of the same harness bug described next, and has been corrected everywhere it was written down. **This item surfaced and fixed two real bugs along the way, both documented in `BUGS_AND_FIXES.md`:** Bug 13, a measurement bug in the test tooling (`_search` silently caps `hits.total` at 10,000 without `track_total_hits=true` — found in `reconcile.py` first, then independently in `run_load_test.sh`'s own separate poll-loop queries, since the same missing parameter was written in two places; both fixed); and Bug 12, a genuine, previously-undocumented data-loss bug in the pipeline itself — the audit-trail branch's document ID collided under sustained load (Bug 4's exact failure mode, reintroduced in a branch that never got Bug 4's actual random-UUID fix applied to it), landing at 55,577 of 89,159 real audit events before the fix, confirmed at exactly 89,159/89,159 after it. **Scoped honestly, not oversold:** this remains a single-machine vertical-scaling test — real, and it found a real bug, but it still can't establish anything about a real multi-node OpenSearch cluster, multiple `redact-service` replicas, or actual terabytes/day volume, which need real infrastructure not available in this project's development environment. See `validation/load_test/README.md` for the full writeup. **Not yet done:** runs at additional sizes (e.g. 1,000,000) to see whether the ~250 lines/sec throughput holds flat or degrades further.

## Research value

10. **DONE (partial), 2026-08-07.** `validation/non_us_name_test.py`: tested the en_US dictionary against flattened names from Faker's German/French/Spanish/Italian providers (largely disjoint from en_US — measured surname overlap 0.5-13.3% depending on locale). Result: **1.4% recall (28/2,000)**, collapsing almost entirely outside the dictionary's own population — direct, measured confirmation of the docstring's "Zhiwei Tan" concern. **Not the originally planned test**: real US Census name-frequency data wasn't reachable from this dev sandbox (no network route to census.gov or the usual nltk/GitHub-hosted corpora), and the one real-world dataset available on PyPI (`names-dataset`) was rejected on inspection — its data is sourced from a documented 2021 Facebook data breach, inappropriate for a PII-protection tool to validate against. Faker's non-US locales were the practical, ethically clean substitute; genuinely informative but still Faker-sourced, so the broader "real production username population" question isn't fully closed. If a legitimate real-world name-frequency source becomes available later (e.g. downloaded manually outside this sandbox and added to the repo), rerunning this same test against it is the concrete next step.
11. **DONE, 2026-08-07.** `validation/entropy_fair_test/`: a dedicated 2,000-entry corpus of the category entropy detection is actually built for (API keys, tokens, hashes), plus UUIDs as a deliberately hard negative case. Initial result: best F1 0.811 (precision 0.811, recall 0.812, 9.7% false-alarm rate) at `min_len=12, threshold=4.2` — versus 2.3%-recall/34.8%-false-alarm on the main corpus, confirming that number was a measurement of the wrong target, not a weak technique. Remaining false positives concentrated almost entirely in UUIDs embedded in URLs/params (confirmed by inspection).

**Follow-on, same day: UUID-shape exclusion added to `scan_entropy()`** (`src/detect.py`). First attempt (anchoring a UUID regex to the whole token) had zero measured effect — root cause: the token regex's own character class includes `/`, `=`, `_`, so a UUID in real log text is never an isolated token, it's swallowed into a longer one along with its path prefix or `key=` name. Fixed by searching for a UUID-shaped *substring* instead of requiring an exact whole-token match. Result: precision 0.811 → **1.000**, false-alarm rate 9.7% → **0.0%**, F1 0.811 → **0.896**, recall unchanged (797/982 TP both before and after — no real secret coincidentally contains a UUID-shaped substring). Verified no regression on the main corpus's own entropy false-alarm measurement (33.9%, unchanged, since it doesn't contain UUID-shaped tokens). Known, stated tradeoff: a small number of real-world services issue UUID-shaped API keys/tokens, which this exclusion would now also suppress — not fixed, documented in `validation/entropy_fair_test/README.md`. Fully regex-only, no spaCy needed, so both rounds were completely testable in this sandbox.
