## Commercial / production-readiness

6. **DONE, fully verified (2026-08-07 and 2026-08-08); cross-process defect found and fixed (2026-08-08, see Bug 14).** Replaced the flat-JSON-only `TokenStore` with an abstract `StorageProvider` interface (`src/anonymize.py`): `FileStorageProvider` (the original behavior, still the default everywhere — `service.py`, `pipeline.py`, `validate.py` all pass a bare path and get wrapped automatically for backward compatibility) and `RedisStorageProvider` (new, for a shared production backend across multiple `redact-service` replicas). **`RedisStorageProvider` verified against a live Redis instance** (`validation/redis_storage_provider_test.py`, run by the user locally against `redis:7`): basic token round trip, persistence across a fresh `TokenStore`/provider instance pointed at the same Redis, tokenize/detokenize round trip, and the same 8-threads-x-200-calls concurrent-access test that originally found the TokenStore race condition (Bug 6) — all passed, zero errors. That test, however, only ever exercised multiple *threads* in one process, not the real production topology (multiple separate `redact-service`/gunicorn-worker *processes* sharing one backend) — a gap flagged explicitly in the original text of this item. **Update 2026-08-08 (Bug 14):** building the actual multi-process test closed that gap and found the gap was hiding a real bug: `TokenStore.save()` did a blind read-once/overwrite-on-every-save, which loses reverse-map entries whenever two processes save concurrently — confirmed in-sandbox (no Docker needed) with `validation/multiprocess_tokenstore_test.py` against `FileStorageProvider`: 58.7% loss pre-fix (plus worker crashes from a non-atomic file write), 14.2% loss after a read-merge-write fix alone, 0% loss after adding real cross-process locking (`FileStorageProvider.lock_for_save()` via `fcntl.flock`; `RedisStorageProvider.lock_for_save()` via a single-node Redis `SET NX PX` + Lua-release lock, deliberately scoped to single-node correctness, not full Redlock). The Redis-backend counterpart of this test (`validation/multiprocess_redis_test.py`) was **run by the user locally against a live Redis instance (2026-08-08)**: 8 processes x 50 tokens each, save-after-every-token, **0 of 400 tokens lost** — `RedisStorageProvider.lock_for_save()`'s cross-process lock confirmed under real separate OS processes, not just logically analogous to the file backend. `RedisStorageProvider` is now fully verified for both single-process thread safety and multi-process safety, matching `FileStorageProvider`. A HashiCorp Vault provider is not implemented; the interface is designed so adding one only requires implementing `load()`/`save()`.

8. **DONE (partial), 2026-08-07; extended, 2026-08-08.** Added `extract_fields_syslog()` to `fields.py`: recognizes KV-style syslog bodies (`sudo`, `kernel` templates) and sshd auth-message shapes (`Failed password for X from Y port Z`, `Invalid user X from Y`, etc.). Measured against the regenerated synthetic corpus: 100% of PII-bearing syslog entries (1,035/1,035) now produce field-level structure (0% before), zero false extractions on 2,347 clean syslog entries, and `drift.py`'s own hit-rate logic correctly separates the PII-bearing fields (`sshd.user` ~48%, `sudo.PWD` ~51%) from the constant ones (`sudo.USER` 0%). No spaCy needed for this verification since it's regex-only, so it was fully testable in this sandbox, unlike items 3-5 above.

   **Extended 2026-08-08** (`validation/syslog_coverage_extension_test.py`, a dedicated small Faker-seeded corpus kept separate from `data/synthetic_logs.jsonl` so this didn't perturb any of the many numbers already tied to that file's exact content): four more common real-world syslog message shapes now covered — sshd `Accepted publickey for X from Y port Z` (key-based auth; the original patterns only had `Accepted password for`, an oversight, not a scope decision), `su` privilege-escalation (`session opened for user root by X(uid=N)`), `useradd`/`usermod` (`name=X, UID=N, GID=N, ...`, comma-separated rather than sudo's semicolon-separated KV), and `dhclient` DHCP lease messages (`DHCPACK from X`, `DHCPOFFER from X`). All five new shapes measured at 100% coverage (500/500 across 100 Faker-generated lines per shape), zero regression on the original shapes (300/300, unchanged), zero false extraction on clean lines including a deliberately-included still-uncovered `cron` line (0/300).

   **A real ordering bug was found and fixed building this test**, not just missing coverage: the `su` and `dhclient` message shapes both legitimately contain a bare `=` in a non-KV context (`by jsmith(uid=0)`, `(xid=0x12345678)`), which used to trigger the function's generic KV-fallback branch first (it only checked `if "=" in rest`) and produce a wrong, nonsensical field (e.g. `su.uid = "0)"`) instead of ever reaching the more specific patterns. Fixed by trying the preposition-shaped patterns before the generic KV fallback, not after — full writeup in the script's own docstring and `extract_fields_syslog`'s.

   **Extended again, 2026-08-08** (`validation/syslog_coverage_extension_round2_test.py`, another dedicated Faker-seeded corpus, same non-perturbing-the-canonical-corpus reasoning as above): three more of the specific gaps the previous paragraph named as still open are now closed — `systemd-logind` session messages (`New session N of user X.`, logged once per login session regardless of auth method, a second independent source of a username in syslog beyond sshd's own messages), `cron` job execution (`(X) CMD (command)`, cron's own standard log format across distributions), and `NetworkManager` DHCP lease messages (`<info> [epoch-timestamp] dhcp4 (iface): address X`, the same leased-IP shape `dhclient` covers under a different daemon's message wrapping). All three new shapes measured at 100% coverage (300/300), zero regression on the 7 previously-covered shapes (700/700, unchanged), zero false extraction on 4 clean-line templates including two deliberately-similar-but-different shapes chosen specifically to prove the new patterns aren't over-broad (`systemd`'s own `Started Session N of user root.` message, distinct from `systemd-logind`'s `New session N of user X.`; and `NetworkManager`'s Wi-Fi P2P message, distinct from its `dhcp4`-address message) — 0/400.

   **A real bug was found and fixed building this round too**, the same "looked like just adding a pattern, actually needed a small fix first" shape as the ordering bug in the previous round: `_SYSLOG_TAG_RE`'s tag character class was a plain `\w+`, which doesn't match the hyphen in `systemd-logind` — the *entire* tag-prefix match failed on every line from this daemon, not just the new message-body pattern, so `extract_fields_syslog` returned `{}` unconditionally for it regardless of what patterns existed. Fixed by widening the tag regex to `[\w-]+`, which also now correctly handles any other hyphenated daemon name (`systemd-resolved`, `systemd-networkd`, etc.) without needing a fix per daemon.

   **Extended a third time, 2026-08-08** (`validation/syslog_coverage_extension_round3_test.py`, another dedicated Faker-seeded corpus, same reasoning as both rounds above): closed all four of the specific gaps round 2's paragraph named as still open — sshd session-teardown messages (`Disconnected from user X Y port Z` / `Disconnected from authenticating user X Y port Z [preauth]`, at least as common in real sshd logs as the login-attempt messages already covered, still carrying a username), `cron` reload messages (`(X) RELOAD (crontab-path)`, the counterpart to the already-covered job-execution `(X) CMD (...)` message), `NetworkManager` Wi-Fi connection messages (`<info> [timestamp] device (iface): Activation: (wifi) connected to 'SSID'`, closing the Wi-Fi-SSID gap round 2's own `dhcp4` pattern comment explicitly left open — an SSID can itself carry a person's name), and `systemd` unit-failure messages (`unit.service: Failed with result 'exit-code'.`, a different systemd subsystem than `systemd-logind`'s session messages, included mainly to close the documented gap since a unit name rarely carries PII on its own). All five new shapes (four message types, with `Disconnected` counted as a single shape covering two auth-outcome wordings) measured at 100% coverage (500/500), zero regression on the 10 previously-covered shapes (1,000/1,000, unchanged, confirmed against rounds 1 and 2's own test scripts too), zero false extraction on 4 clean-line templates chosen to prove the new patterns aren't over-broad (a `Connection closed by` sshd variant with no username in this wording; cron's own generic `(CRON) INFO (...)` startup message, not a real username; a systemd unit *starting*, not *failing*; and `NetworkManager`'s Wi-Fi P2P message, still distinct from the new Wi-Fi-connection pattern) — 0/400.

   **Still explicitly partial**: message shapes outside this now-16-pattern list (other NetworkManager message types beyond DHCP leases and Wi-Fi connections — interface state changes, policy decisions; other systemd message types beyond unit-failure and login sessions — unit start/stop, timers; and any auth-message wording still outside the expanded sshd list) still get zero fields, same as before — a production deployment with different syslog traffic needs its own additional patterns, following the same approach. This is now the third consecutive round to find and close a batch of the "still open" gaps the previous round named; the pattern suggests this could continue indefinitely for a sufficiently exotic log source, which is exactly why this docstring keeps stating the scope honestly each time rather than ever claiming syslog coverage is complete.

**Unplanned but significant side finding, fixed the same session:** measuring whether `drift.py` actually caught injected drift in a newly-covered syslog field surfaced Bug 11 (`BUGS_AND_FIXES.md`) — `field_stats()` never called `scan_flattened()`, so drift detection was structurally blind to flattened-username PII in every field it monitors, in every log type, since Layer 4 was added. Fixed (now included by default, `use_ner` made an optional parameter for testing without spaCy). Confirmed via injection test: previously silent, now correctly flagged. One honest side-effect also found: the flattened layer's ~50% recall produces enough sample-to-sample variance to occasionally cross the default 5% drift threshold on a stable corpus — noted, not treated as a defect, see Bug 11 for the full writeup. **`validate.py`'s own (NER-dependent) Section 5 drift check was rerun by the user locally against the fix**, confirming the same side-effect independently: 16/18 checks pass overall, with the 2 failures both in Section 5 and both matching the documented pattern (`syslog.sshd.user` riding along as a false positive alongside correctly-caught real drift) — see Bug 11 in `BUGS_AND_FIXES.md` for the full numbers.

**2026-08-08: run at 1,000,000 lines — FAILED, and found the most consequential bug of this entire roadmap (Bug 15, `BUGS_AND_FIXES.md`).** The run's own reconciliation reported FAIL (728,125 of 1,000,000 expected events at harness exit), and live investigation confirmed this wasn't the harness quitting early on a slow patch (the leading theory at first) — ingestion was still genuinely, severely stalled minutes later (916,500 and barely climbing), with `redact-service` pegged at ~110% CPU producing ~3 events/sec while `redact-logstash` sat nearly idle waiting on it, and zero errors anywhere in any container's logs. Root-caused directly: `docker exec redact-service ls -la /app/output/` showed `token_store.json` at 12.4MB/93,279 entries, and a single live request timed with `curl` took 2.927s. `TokenStore.save()` (the fix Bug 14 introduced) does a full read-merge-write of the ENTIRE persisted store on every call, and `service.py` calls it after every single request — O(n) cost per request, O(n²) total across a run, invisible at every scale tested before this one (10,000 and 100,000 lines both stayed too small to cross the point where this became noticeable). **A debounce mitigation was applied and verified in-sandbox the same day** (`save_every_n_calls` parameter, `service.py` now defaults to a real write once every 25 requests instead of every one; confirmed via a new dedicated test, `validation/tokenstore_save_scaling_test.py`, showing ~47x less total time spent in `save()` with zero regression on the existing multi-process zero-loss tests) — but this is a mitigation, not a fix (same O(n) shape, just paid less often), and introduces a new bounded crash-recovery-window tradeoff. **Re-run against the mitigation, same day — PASS.** After tearing down the stuck stack (`docker compose down -v`) and rebuilding, a fresh `run_load_test.sh 1000000` run reported its own `FAIL` at exit (938,000/1,000,000 after the harness's poll loop hit its fixed 240-iteration cap) — but manually re-running `reconcile.py` minutes later showed the count still climbing steadily (971,625 → 981,750 over 180s, ~56 events/sec, clearly not stalled), and a further 600s wait produced a clean, complete result: **`security-logs-anonymized-*` = 1,000,000 exact, `security-logs-quarantine-*` = 0 exact, `redact-audit-trail-*` = 893,150, reconciliation PASS.** 89.315% audit fan-out closely matches the 100,000-line run's 89.159%, confirming correctness held at 10x scale, not just completion. Total time to full completion: under ~75 minutes, ~224 lines/sec average across the *entire* run — close to the 100,000-line baseline's ~250 lines/sec despite the store growing to hundreds of thousands of entries along the way. **Separate, minor finding from this rerun:** the load-test harness's own poll loop gave up after a fixed 240 iterations rather than truly adaptive stability detection, so it reported a false `FAIL` here even though the pipeline was healthy and converging. **Fixed, 2026-08-08**: `run_load_test.sh` now uses a wall-clock deadline (`REDACT_LOAD_TEST_MAX_WAIT_SECONDS`, default 4 hours) instead of a fixed iteration count — syntax-checked, not yet re-verified against a live Docker run (needs the user's machine; the next full-scale load test will confirm it in practice). **The real Bug 15 fix, also 2026-08-08, same day:** the debounce mitigation was always disclosed as not a fix — the O(n)-per-save cost was unchanged, just paid less often. That's now actually fixed: `StorageProvider` gained `save_incremental()`, persisting only newly-minted entries instead of the whole store — `RedisStorageProvider` via a per-key `HSET` of just the new batch (no lock needed, safe by construction), `FileStorageProvider` via an append-only write-ahead log with periodic compaction (default every 200 batches) instead of a full JSON rewrite on every save. Verified in-sandbox: `multiprocess_tokenstore_test.py` still shows 0/400 lost; `tokenstore_save_scaling_test.py` (rewritten to reflect the new result) now shows a 1.1x growth factor at 23x the store size — essentially flat, not the prior mitigation-only run's 10-22x — even with the debounce fully off (`save_every_n_calls=1`); a new test, `wal_compaction_correctness_test.py`, confirms 0/5,000 tokens lost across ~100 forced WAL compactions, both same-process and via a fresh `TokenStore` simulating a restart. **Redis path confirmed, 2026-08-08, run by the user locally:** `validation/multiprocess_redis_test.py` re-run against a live `redis:7` container — 0/400 reverse-map entries lost, closing the one gap left when this fix first landed. Both `StorageProvider` implementations are now verified live for the incremental-write path, not just the file backend. See Bug 15 in `BUGS_AND_FIXES.md` for the complete writeup, including why `compact()`'s own O(n) cost, while now far rarer, is not eliminated entirely.

## Research value

10. **DONE, 2026-08-08 — the originally planned test, fully closed out.** `validation/non_us_name_test.py` (2026-08-07): tested the en_US dictionary against flattened names from Faker's German/French/Spanish/Italian providers (largely disjoint from en_US — measured surname overlap 0.5-13.3% depending on locale). Result: **1.4% recall (28/2,000)**, collapsing almost entirely outside the dictionary's own population — direct, measured confirmation of the docstring's "Zhiwei Tan" concern, but still Faker-sourced data on both sides, not the originally planned real-population test. **2026-08-08: unblocked and run.** The user downloaded two legitimate, public-domain, aggregate US government name-frequency sources via `validation/real_name_frequency/download_name_data.sh` — SSA "Popular Baby Names" (52,739 distinct given names, national data 2016-2025) and the US Census Bureau's 2010 surname frequency table (162,253 surnames occurring 100+ times) — both explicitly stated by their publishers as not identifying individuals, the same standard that got `names-dataset` rejected. `validation/real_name_frequency/build_real_name_test.py` samples 2,000 `<given><surname>` flattened tokens **weighted by real frequency** (not uniform sampling — a deliberate methodological choice to simulate a realistic, Zipfian production username population rather than treating a once-in-145-years 5-occurrence name the same as "James"). **Result: 15.2% recall (305/2,000)** — squarely between the 50.3% Faker-matched number and the 1.4% non-US-locale number, exactly where a real population should land. **Mechanism, not just the number:** dictionary coverage alone is low (Faker's ~700 first names cover only 1.3% of distinct real given names, though 31.3% of the real population by frequency, since common names concentrate most of the mass; surnames similarly 0.6% distinct / 45.3% weighted) — but a second, independent gap compounds it: real usage increasingly gives people surname-shaped first names (Foster, Kennedy, Hunter, Mason, etc., a real, measured modern SSA trend), which Faker's dictionary classifies as `LAST_NAMES`-only, so `_segment_match()` correctly finds no valid split even though both halves are technically "in the dictionary." When a sampled pair actually filled the dictionary's expected first/last roles, recall was 305/306 = 99.7% (the one exception being a length-bound edge case, `sarahli`, not a coverage gap) — direct confirmation the segmentation algorithm itself works correctly whenever its inputs are covered; the shortfall is entirely a dictionary-coverage-and-role problem, not an algorithmic one. See `validation/real_name_frequency/raw/README.md` for the full source citations.
11. **DONE, 2026-08-07.** `validation/entropy_fair_test/`: a dedicated 2,000-entry corpus of the category entropy detection is actually built for (API keys, tokens, hashes), plus UUIDs as a deliberately hard negative case. Initial result: best F1 0.811 (precision 0.811, recall 0.812, 9.7% false-alarm rate) at `min_len=12, threshold=4.2` — versus 2.3%-recall/34.8%-false-alarm on the main corpus, confirming that number was a measurement of the wrong target, not a weak technique. Remaining false positives concentrated almost entirely in UUIDs embedded in URLs/params (confirmed by inspection).

**Follow-on, same day: UUID-shape exclusion added to `scan_entropy()`** (`src/detect.py`). First attempt (anchoring a UUID regex to the whole token) had zero measured effect — root cause: the token regex's own character class includes `/`, `=`, `_`, so a UUID in real log text is never an isolated token, it's swallowed into a longer one along with its path prefix or `key=` name. Fixed by searching for a UUID-shaped *substring* instead of requiring an exact whole-token match. Result: precision 0.811 → **1.000**, false-alarm rate 9.7% → **0.0%**, F1 0.811 → **0.896**, recall unchanged (797/982 TP both before and after — no real secret coincidentally contains a UUID-shaped substring). Verified no regression on the main corpus's own entropy false-alarm measurement (33.9%, unchanged, since it doesn't contain UUID-shaped tokens). Known, stated tradeoff: a small number of real-world services issue UUID-shaped API keys/tokens, which this exclusion would now also suppress — not fixed, documented in `validation/entropy_fair_test/README.md`. Fully regex-only, no spaCy needed, so both rounds were completely testable in this sandbox.
